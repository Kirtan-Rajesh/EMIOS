VDI Setup and Repository Bootstrap

Every VDI must use the same repository structure and service ports so the team does not waste time debugging environment mismatch.

  • Clone the shared repo into a stable root folder such as C:\hackathon\EMIOS or the equivalent on each VDI.
  • Use the same Python version on every machine. Python 3.11 is the target.
  • Create a virtual environment inside the repo root named .venv.
  • Install backend dependencies from backend/requirements.txt.
  • Create backend/.env from the example file and set the Neo4j credentials and any optional LLM keys.
  • Start Docker Desktop or equivalent container runtime and bring up the services from docker-compose.yml.
  • Keep the same local ports across all machines: backend on 8000, Neo4j browser on 7474, Neo4j Bolt on 7687, Qdrant on 6333.

Required local environment flow:

  1. Clone repo and switch to the assigned feature branch.
  2. Create Python environment and install dependencies.
  3. Start Neo4j and Qdrant via Docker Compose.
  4. Run the backend and verify /api/health.
  5. Run tests before pushing any major change.

A project that runs on one VDI but fails on another is a demo risk. The environment setup must be identical across all machines.

Critical Missing Layer: Persistence and Data Model for Workable APIs

The current repository already has graph-oriented logic and API endpoints, but it does not yet have a durable business-data layer for real assessment workflows. For the APIs to be production-usable and hackathon-credible, the team must add a lightweight persistence model.

Recommended approach for this hackathon: use SQLite for metadata persistence and keep Neo4j for the graph/digital twin. This keeps deployment simple, cheap, and fast.

Persistence Model to Implement

  • assessments — stores assessment metadata such as customer name, project name, target cloud, status, created_at, updated_at.
  • assessment_uploads — stores file metadata and upload timestamps for each assessment.
  • assessment_nodes — stores normalized systems/components derived from the uploaded input.
  • assessment_edges — stores dependency relationships between systems.
  • agent_runs — stores each agent execution with agent name, status, start/end timestamps, and output summary.
  • migration_waves — stores recommended migration waves and their assigned components.
  • assessment_reports — stores report snapshots, summary text, confidence score, and generated timestamps.

Relationships:

  • One assessment has many uploads.
  • One assessment has many nodes and edges.
  • One assessment has many agent runs.
  • One assessment has many migration waves.
  • One assessment has one report snapshot.

1. Implement Assessment Lifecycle API

Owner: Kunal

Goal: Allow the app to create, retrieve, and update assessment records.

  • Implement POST /api/v1/assessments to create a new assessment with customer name, project name, target cloud, and status.
  • Implement GET /api/v1/assessments/{assessment_id} to fetch the assessment details.
  • Implement PATCH /api/v1/assessments/{assessment_id}/status to update status such as uploading, analyzing, complete, failed.

Success output: assessment_id, customer_name, project_name, target_cloud, status, created_at, updated_at.

Dependency: Must be implemented before any assessment-specific endpoint can be considered complete.

2. Implement Upload Metadata API

Owner: Kunal + Kirtan

Goal: Store upload metadata and link uploaded data to an assessment.

  • Implement POST /api/v1/assessments/{assessment_id}/uploads to record uploaded files and their metadata.
  • Implement GET /api/v1/assessments/{assessment_id}/uploads to fetch all uploads for a specific assessment.
  • Store file name, content type, upload timestamp, source type, and storage reference.

Success output: upload_id, assessment_id, filename, uploaded_at, status.

Dependency: Depends on the assessment lifecycle API.

3. Implement Assessment Graph Persistence API

Owner: Kirtan

Goal: Persist normalized nodes and edges for an assessment so the graph is not only transient.

  • Implement POST /api/v1/assessments/{assessment_id}/graph to save the normalized node and edge data.
  • Implement GET /api/v1/assessments/{assessment_id}/graph to retrieve the graph for that assessment.
  • Store the graph payload in the relational tables and also keep the Neo4j graph in sync for UI display.

Success output: node_count, edge_count, assessment_id, graph_status.

Dependency: Depends on the upload metadata API and the ingestion normalization flow.

4. Implement Simulation Result API

Owner: Bhargavi

Goal: Store simulation results for a saved assessment.

  • Implement POST /api/v1/assessments/{assessment_id}/simulate to run the impact and Monte Carlo simulation.
  • Persist the results including impacted services, revenue at risk, total hosting cost, and confidence values.
  • Implement GET /api/v1/assessments/{assessment_id}/simulate to return the stored result.

Success output: impacted_services, revenue_at_risk, total_hosting_cost, potential_savings, monte_carlo.

Dependency: Depends on the assessment graph persistence API.

5. Implement Migration Wave API

Owner: Bhargavi + Kunal

Goal: Save and retrieve the migration wave plan.

  • Implement POST /api/v1/assessments/{assessment_id}/waves to store the planner output.
  • Implement GET /api/v1/assessments/{assessment_id}/waves to retrieve the waves.
  • Store wave number, assigned components, and rationale for each wave.

Success output: waves array with wave number, components, rationale, risk summary.

Dependency: Depends on the simulation result API and planner logic.

6. Implement Agent Run and Observability API

Owner: Bhargavi

Goal: Track what each agent did and make the workflow visible.

  • Implement GET /api/v1/assessments/{assessment_id}/agent-runs to fetch previous agent execution records.
  • Store status, timestamps, agent name, and output summary for each run.
  • Expose a simple observability summary endpoint for the frontend.

Success output: agent_runs array including agent name, status, started_at, completed_at, summary.

Dependency: Depends on the assessment lifecycle API.

7. Implement Dashboard Summary API

Owner: Kunal

Goal: Provide the frontend with the high-level dashboard data it needs.

  • Implement GET /api/v1/dashboard/summary to return total assessments, completed assessments, active assessments, and latest report status.
  • Use the persisted assessment records rather than only in-memory data.

Success output: total_assessments, completed_assessments, active_assessments, latest_assessment_id.

Dependency: Depends on the assessment persistence layer.

8. Implement Report Snapshot API

Owner: Shweta + Bhargavi

Goal: Make the report output reusable and shareable.

  • Implement GET /api/v1/assessments/{assessment_id}/report to retrieve a summarised report snapshot.
  • Store executive summary, migration readiness, risk summary, waves, and top recommendations.

Success output: executive_summary, readiness_score, risk_summary, migration_waves, recommendations.

Dependency: Depends on the wave and simulation APIs.

Specific Task Specifications

  • Implement POST /api/upload that accepts sample ingestion data and returns parsed counts and warnings.
  • Implement GET /api/graph that returns a graph payload.
  • Implement POST /api/simulate that returns simulation output.
  • Implement POST /api/plan that returns migration waves.

Output: Consistent JSON structure for frontend integration and backend testing.

Dependency: Must be completed before frontend integration and agent integration.

2. Implement Upload and Ingestion Pipeline

Owner: Kirtan

Goal: Turn uploaded metadata into structured application and dependency data.

  • Accept sample JSON/CSV-like payloads.
  • Normalize each item into a node structure with id, name, type, complexity, annual cost, and runtime.
  • Normalize dependency rows into edge structures.
  • Handle duplicate IDs and invalid links gracefully.
  • Return validation warnings/errors in the response.

Output: A clean list of nodes and edges ready for graph and simulation engines.

Dependency: Uses the API contract from Kunal.

3. Implement Digital Twin Graph Persistence and Retrieval

Owner: Kirtan

Goal: Make the dependency graph available as the digital twin view.

  • Store ingested nodes and edges in the graph store.
  • Implement graph retrieval for the UI.
  • Return node labels, node categories, and edge relationships in a frontend-friendly format.
  • Ensure graph traversal is possible for downstream simulation logic.

Output: A usable graph payload for the UI and for assessment logic.

Dependency: Depends on the ingestion output produced by Kirtan’s pipeline.

4. Implement LLM Orchestration and Agent Workflow

Owner: Bhargavi

Goal: Make EMIOS feel intelligent through coordinated agents.

  • Implement the discovery, dependency, planner, and risk agents.

  • Ensure the agent logs are usable for the UI.

Output: A structured assessment summary with logs, risks, and proposed waves.

Dependency: Depends on the graph and assessment data shape from the backend contract.

5. Implement Simulation Engine for Impact and Estimation

Dependency: Depends on the graph representation and assessment schema.
